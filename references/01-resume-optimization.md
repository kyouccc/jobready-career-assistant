# 01 · 简历优化

## 执行前提

必须拿到三样：**目标岗位、目标行业（或公司梯队）、简历原文**。缺任意一项先追问，不要凭猜测改。
若用户同时给了 JD，先走 `02-jd-analysis.md` 提取关键词，再回到本文件做覆盖度改写 —— 这是效率最高的顺序。

## 零、输入材料处理（先解决读取，再谈改写）

用户给的简历通常是 PDF 或 Word，不是纯文本。**读取失败或读取不全，后面全白做。**

| 格式 | 处理方式 |
|---|---|
| 纯文本 / Markdown | 直接使用 |
| PDF | 用 Python 提取文本层，见下方「PDF 提取实操」 |
| DOCX | 用 python-docx 读取；或用本地 Office 编辑技能打开 |
| 图片 / 扫描件 | 无文本层，改走多模态读图 |

### PDF 提取实操

`Read` 工具读 PDF 有 256KB 上限，简历 PDF 常因嵌入字体而超过该限制。改走 pypdf：

```bash
pip install pypdf   # 若环境无该库
python -c "
from pypdf import PdfReader
r = PdfReader(r'<简历路径>')
print('页数:', len(r.pages))
for i, p in enumerate(r.pages, 1):
    print('--- 第 %d 页 ---' % i)
    print(p.extract_text() or '（无文本层）')
"
```

**若返回「（无文本层）」**：这是扫描件或图片型 PDF，需改用读图方式。
**不要凭猜测补内容** —— 直接告知用户「这份 PDF 没有文本层，请提供 Word 版或直接粘贴文字」。

**提取后必须通读一遍再动笔**，核对三件事：
1. 联系方式、时间线是否完整（PDF 提取常丢分栏内容）
2. 项目条数是否与用户口述一致（丢表格会导致整段项目消失）
3. 是否出现明显的字符错乱或断裂 —— 有则回头核对原文

> **实战教训**：用户提供的 PDF 简历可能**本身就有缺项**（例如某个项目根本没写进去）。
> 若你在其他上下文（历史对话、用户档案）里知道用户有某段经历，而简历里没有，
> **要主动指出来并请用户确认**，不要默认「简历里没有就是没有」。
> 漏掉一个带量化指标的项目，可能正是整份简历最该补的东西。

## 一、简历的唯一评价标准

一份简历是否有效，只看三个问题：

1. **HR 初筛 8 秒内能否定位「这个人为什么匹配这个岗」？**（匹配度）
2. **每条经历能否看出「做了什么 → 产出是什么 → 影响多大」？**（可验证性）
3. **机器（ATS）能否正确解析并命中 JD 关键词？**（可检索性）

三者优先级：匹配度 > 可验证性 > 可检索性。学生简历 90% 的问题出在第 2 条。

## 二、STAR 改写公式

**基础结构**：`动词 + 动作对象 + 方法/技术 + 结果（量化）`

不要写成叙事：「负责 XX 模块的开发工作，参与了项目从 0 到 1 的过程。」

要写成结果句：

| 要素 | 说明 | 反面示例 | 正面示例 |
|---|---|---|---|
| S 情境 | 一句话交代背景，可省 | 「在项目开发中」 | 「面向 5 万级日活场景」 |
| T 任务 | 你负责的边界 | 「负责部分功能」 | 「独立负责订单模块 12 个接口」 |
| A 行动 | 技术选型 + 关键决策 | 「使用了一些技术」 | 「用 Redis 预扣减 + 本地消息表解决超卖，QPS 从 800 提升至 3400」 |
| R 结果 | 数字 + 对比基准 | 「效果良好」 | 「超卖率归零，接口 P99 从 620ms 降至 90ms」 |

**高阶变体（技术岗更吃香）**：`问题 → 方案对比 → 选型理由 → 结果 → 反思`
例：「原方案用轮询同步数据，延迟 30s 且空转耗 CPU。对比 WebSocket 与 SSE 后选择 SSE（单向推送、实现成本低、断线自动重连），延迟降至 1s 内，服务器 CPU 占用下降 18%。」

## 三、量化补全：用户没有数字怎么办

**这是简历优化最高频的卡点。绝对不要替用户编数字。** 按以下顺序引导：

1. **先问四类可回忆的量**（用户通常记得，只是没意识到是「成果」）：
   - 规模：数据量、用户数、并发、代码行数、团队人数、时长
   - 效率：耗时从 X 到 Y、人力从 N 人降到 M 人、自动化节省工时
   - 质量：准确率/召回率/F1、崩溃率、Bug 数、覆盖率、延迟
   - 覆盖：支持多少种场景/机型/协议、上线多少个版本、被多少人使用
2. **若无精确值，用可验证的区间或排名**：「覆盖 3 类主流机型」「在 40 人班级中排名前 5」「校内赛一等奖（前 3%）」。
3. **实在无量化时，用「可复用的复杂度」替代**：说明技术难点本身即为亮点（如「自研协议解析器，兼容 4 种私有帧格式」）。
4. **仍然空缺则写占位符** `【待确认：XX 数值】` 并在报告末尾附「需要你补充的信息」清单。

## 四、动词与措辞规范

- **强动词开头**（体现主动性）：主导、设计、实现、重构、优化、搭建、落地、复现、迁移、自动化、定位并修复、推动。
- **弱动词替换**：`负责`→`主导/独立实现`；`参与`→`承担 XX 模块`；`协助`→`支持 XX 环节（占比约 N%）`；`学习`→`复现/应用`（简历不写学习过程，写产出）。
- **删掉无信息量的词**：精通（无佐证别写）、熟练掌握（改为「用于 XX 场景」）、积极配合、认真负责、沟通能力强（用事实体现，不用形容词）。
- **技术名词大小写统一**：`PyTorch`/`PyTorch` 不要混写 `pytorch`；`HarmonyOS`/`ArkTS`/`Jetpack Compose` 保持官方写法。

## 五、ATS 关键词矩阵

ATS（简历筛选系统）按关键词命中打分。做法：

1. 从 JD 抽出关键词，分三档：
   - **A 档 · 硬技能**：编程语言、框架、工具、证书、学历门槛 —— 必须逐字命中（如 JD 写 `PyTorch`，别只写 `深度学习框架`）。
   - **B 档 · 领域词**：业务域、方法论（如 `目标检测`、`模型量化`、`RAG`、`分布式`）。
   - **C 档 · 素质词**：跨团队协作、抗压、owner 意识 —— 命中即可，不必堆砌。
2. 做一张覆盖度表：

| 关键词 | 档位 | JD 出现次数 | 简历是否命中 | 命中位置 |
|---|---|---|---|---|
| PyTorch | A | 2 | ✅ | 项目 2 |
| 模型量化 | A | 1 | ❌ | — 建议补入项目 3 |

3. **命中原则**：能真实命中就命中；不能真实命中的**不许硬塞**（面试会被拆穿）。此时归入「差距补全建议」，给出学习路径。

## 六、格式体检清单（逐条打勾）

- [ ] 一页（应届/实习）；社招初阶最多两页
- [ ] 无照片、无性别/身高/婚育等无关信息（国内部分国企除外，按用户场景判断）
- [ ] 联系方式：手机 + 邮箱，邮箱用 `姓名@域名` 形式，不用中二昵称
- [ ] 时间倒序，格式统一（如 `2025.09 – 2029.06`）
- [ ] 每段经历 3–5 条 bullet，每条不超过 2 行
- [ ] 无错别字、无中英标点混用、无字体混排
- [ ] 技能栏分级清晰（精通/熟悉/了解），且与经历互相印证
- [ ] 导出 PDF 后检查分页是否截断、有无乱码

> **约定**：交付时同时给 PDF（投递打印）与 Word/Markdown（后续编辑）两版。

## 七、结构层决策：删什么、留什么、什么当主轴

逐段改写只是「把话说好」。**真正拉开差距的是结构层决策** —— 决定哪些内容根本不配出现在简历上。
这一节的方法论优先级高于第二～六章。

### 7.1 版面是零和博弈

一页简历的容量固定。**每加一条，必须对应删一条。** 看到「这条也挺好，加上吧」的冲动时，
先问：它挤掉的是谁？如果挤掉的是与岗位强相关的内容，那就是亏的。

应届生简历最常见的浪费是「**同一件事说两遍**」：
- 顶部「个人亮点 / 自我评价」把下面的项目经历摘要一遍
- 「专业背景」把教育背景与技能栏再抄一遍

判断方法：把每个板块的内容与项目经历做逐条比对，**重复率超过 50% 的板块直接删除**。
它占用的版面足以放下一个完整的项目。

### 7.2 删除判据（三问）

对每一段内容问三个问题，任一为「否」就考虑删除或压缩：

1. **目标岗位的人会关心这条吗？** —— 投 CV 岗时，大模型工程、移动端上架、技术博客都是噪音。
2. **它能被验证吗？** —— 有数字、有名次、有可展示的产物。纯形容词（认真负责、沟通能力强）不可验证。
3. **删掉它，我会失去什么不可替代的信息？** —— 如果答案是「失去一个全链路落地能力的证据」，
   那就**压缩到一行保留**，而不是整段删除。

**压缩优于删除**：把 2 条 bullet 压到 1 行，既保留信号又腾出版面。这是最常用的处理方式。

### 7.3 项目主轴排序判据

简历的第一个项目决定 HR 对你的定位。排序按此优先级：

| 优先级 | 判据 | 说明 |
|---|---|---|
| 1 | **与岗位的直接相关度** | 投感知岗，语义分割 > 图像分类 > 移动端开发 |
| 2 | **指标的可验证性** | 有量化指标的排在只有描述的前面 |
| 3 | **产出的稀缺性** | 期刊投稿、竞赛名次、上架应用 > 课程作业 |
| 4 | **完成度** | 已交付的 > 进行中的 > 计划的 |

**注意**：不要默认「最花时间的项目 = 最该放前面的项目」。
学生容易把投入最多的项目放第一，但如果它与岗位无关，就是浪费黄金位置。

### 7.4 岗位方向细分（同一职类，考察点可能完全不同）

**这是求职者最容易忽略、也最容易吃亏的一点。** 同一个职类下，不同方向要求的技能几乎不重叠：

| 职类 | 方向 | 核心考察点 |
|---|---|---|
| CV / 视觉算法 | 自动驾驶感知 | 目标检测、语义分割、3D 点云、BEV、多传感器融合、模型部署 |
| CV / 视觉算法 | 规划控制 | 几何、轨迹优化、运动学、C++ 工程 |
| CV / 视觉算法 | SLAM | 多视图几何、特征匹配、非线性优化、标定 |
| CV / 视觉算法 | 医疗影像 | 分割、小样本、可解释性、数据合规 |
| CV / 视觉算法 | 生成 / 多模态 | 扩散模型、Transformer、大规模训练 |
| 算法工程 | 推荐 / 广告 | 特征工程、排序模型、A/B 实验 |
| 后端开发 | 基础架构 | 分布式、并发、数据库、稳定性 |

**执行要求**：确认目标岗位后，**必须追问方向**（如「投自动驾驶的感知岗还是规划控制岗？」）。
方向不明时，先按该职类最主流的方向给通用版，并**明确声明所采用的假设**。
若用户只说了「CV 算法实习」，默认按「感知方向」处理，并提示用户确认。

### 7.5 顶部摘要的写法

应届生无实习背书时，顶部一行摘要承担「让 HR 8 秒内定位」的职能。写法：

```
【方向关键词 1】/【方向关键词 2】｜【最有分量的产出】｜【可验证的荣誉】
```

- 只放**目标岗位会抓的关键词**，无关方向一律不放
- 「最有分量的产出」优先用模型名或指标（ATS 会抓模型名）
- 一行以内，不要写成句子

**反面示例**：`CV 分割 / 3D 点云 / 大模型工程 ｜ JCR Q2 投稿 · 应用已上架华为应用市场`
（「大模型工程」「应用上架」对感知岗是噪音，占了最贵的位置）

### 7.6 技能栏的写法

1. **按岗位相关度分组**，无关分组直接删除。投 CV 岗时不要把「大模型」「移动端」单列。
2. **每条技能后面跟使用场景**。没有佐证的分级等于没有分级：
   - 差：`Python（熟练）/ Java / C++`
   - 好：`Python（主力，模型训练与数据处理）、C++（熟悉，算法题与工程实现）、Java（了解）`
3. **只写简历里能印证的技术**。写了 `OpenMMLab` 但项目里没出现，面试官会逐个追问，答不上来比不写更伤。
4. **主动加一栏「在学」**，把缺口变成进行中的规划：

```
· 在学：目标检测（YOLO 系列）、BEV 感知、多传感器融合
```

这条技巧很有效：把「被发现的短板」转化为「自我认知清晰的候选人」。
**前提是如实** —— 写了「在学」就要真的在学，面试会问进度。

### 7.7 交付物落地

`references/01` 约定的「同时给 PDF + Word 两版」需要真正生成文件：

- **Word（可编辑）**：用文档生成技能产出 .docx
- **PDF（投递打印）**：由 Word 转换，或直接生成 PDF
- **交付前必查**：导出后检查分页是否截断、有无乱码、字体是否嵌入

**执行顺序**：不要在数据未补齐时就生成最终成品 —— 会产出一份满是 `【待确认】` 的文件。
正确顺序是「先出改写报告 → 用户补齐数据 → 再生成 Word/PDF 成品」。

## 八、输出结构（严格三段）

**① 整体评价与核心修改方向**
- 一句话结论（当前简历最致命的问题是什么）
- 3–5 条核心问题，按严重度排序
- 匹配度打分（如「与目标 JD 关键词覆盖度 58%，主要缺口在 X/Y」）

**② 逐段改写后的完整简历**
- 给出可直接复制的全文
- 每条改写后用引用块标注：`> 修改原因：原句无量化 / 未体现技术选型 / 关键词缺失`
- 无数据处保留 `【待确认：…】`

**③ 针对目标岗位的加分项补充建议**
- 短期可补（1–2 周内能做的：补一个项目、考一个证、刷一类题）
- 长期可补（需要 1–3 个月）
- 结尾附「需要你补充的信息」清单
